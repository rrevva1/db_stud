### Краткая теория

#### SQL и реляционная алгебра

Реляционная алгебра оперирует **отношениями** (множествами кортежей) и операциями:

| Алгебра | SQL (приблизительно) |
|---------|----------------------|
| σ (выбор) | `WHERE` |
| π (проекция) | `SELECT` столбцов |
| ⋈ (соединение) | `JOIN` |
| ∪, ∩, − | `UNION`, `INTERSECT`, `EXCEPT` |
| ρ (переименование) | алиасы AS |

SQL **богаче** алгебры: ORDER BY, NULL, агрегаты, оконные функции, CTE — этого нет в классической алгебре Кодда.

#### Bag vs Set

**Теория:** отношение — **множество** кортежей (дубликаты запрещены).

**SQL:** таблица по умолчанию — **мешок (bag)**; дубликаты строк допустимы, пока нет UNIQUE/PK.

```sql
CREATE TABLE bag_demo (x int);
INSERT INTO bag_demo VALUES (1), (1), (2);
SELECT x FROM bag_demo;  -- три строки, не две
```

`SELECT DISTINCT` приближает результат к множеству.

#### Трёхзначная логика и теория

К. Дж. Дейт критикует NULL как «не реляционный». SQL принял NULL как отсутствие значения → UNKNOWN в предикатах. Практика: `IS NULL`, `COALESCE`, осторожность с NOT IN.

#### Аномалии SQL как языка

1. **Duplicate semantics** — без DISTINCT результат не гарантированно множество.
2. **ORDER BY без LIMIT** — сортировка не часть реляционной модели (это presentation).
3. **UPDATE без ключей** — может затронуть «неожиданные» дубликаты в bag-модели.
4. **View updating problem** — неоднозначность DML через VIEW (см. урок p4-l05).

#### Антипаттерны (критический взгляд)

| Антипаттерн | Проблема | Лучше |
|-------------|----------|-------|
| SELECT * в production | Хрупкость при изменении схемы | Явный список столбцов |
| NULL как «магическое» значение | UNKNOWN, NOT IN ловушки | Отдельные флаги, NOT EXISTS |
| Неявные JOIN (старый стиль) | Путаница с CROSS JOIN | Явный INNER JOIN |
| Группировка «на глаз» | Столбцы вне GROUP BY | Полный GROUP BY или оконные функции |
| «EAV всё в одной таблице» | Нет типизации, сложные запросы | Нормализованная схема |

#### Реляционное vs физическое

SQL смешивает **декларативный** уровень (что нужно) и **физические** подсказки (`SET enable_seqscan`). Теория отделяет логическую модель от реализации; оптимизатор PostgreSQL закрывает разрыв.
